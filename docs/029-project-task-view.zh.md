## 0. 结论摘要

| # | 结论 | 为什么 | 影响 |
| --- | --- | --- | --- |
| 1 | **项目不是 Ticket，也不是新的授权聚合。** 项目是根 Ticket 之上的一层展示/组织覆盖层；根 Ticket 仍是唯一的授权工作单元。 | 项目是持续的工作方向（A 系统开发、B 机器人研究、C 旅行计划），没有单一交付物、没有结束条件、没有 Mandate；把它做成 Ticket 会产生第二个授权根，并在一个任务完成时错误地结束整个项目。 | 不新增 `Project` 授权实体、不新增 Mandate/Decision/Approval；项目不能批准、不能外发、不能执行。 |
| 2 | **只新增一份可持久化的覆盖层：项目目录（项目 + 根 Ticket 归属）。** 复用任务视图架构提案（`docs/tasks-view-architecture.zh.md`）的 `TaskCategory`/`TaskPlacement` 形状，用户可见名称改为「项目」，并补 `owner`、`goal`、`state`。 | 项目要能聚合多个根 Ticket、有负责人和一句话目标，但不需要改 Ticket 表；现有 `Ticket` 的读写、授权、结束条件都不动。 | 存在 KV 文档 `task-catalogue.v1`；没有项目时读作空，旧界面/旧客户端不受影响。 |
| 3 | **层级固定为：项目 → 根 Ticket（任务）→ 子 Ticket（子任务）→ 更深子 Ticket。** 每个 tracked 节点有自己的 owner/worker；review Ticket 挂在被审任务下，不算项目任务；execution unit（Assignment/Session/subagent）不是任务层级。 | 现有 `Ticket.parentTicketId`/`rootTicketId`/`delegation` 已经能表达子任务，且子 Ticket 已有自己的 owner/worker 和向父负责人汇报的审查链；项目只需要在其上做分组。 | 项目详情是一棵真树；没有子 Ticket 的任务就是叶子，不伪造层级。 |
| 4 | **项目负责人 = 一个既有 AgentProfile（或“默认执行配置”）的默认绑定，不是权限。** 项目只保存 `ownerProfileId`，新根 Ticket 在受理时把该 profile 的当前版本快照进 `Ticket.profile`；已有 Ticket 不被改写。 | 当前 `Ticket.profile` 在受理时冻结；项目负责人若存成版本快照，会把旧配置强加给未来任务。存 id、读当前 head、受理时再快照，既符合现有语义，也不破坏历史。 | 换项目负责人只影响之后的新任务；项目卡要说明「已有任务按各自配置执行」。没有可用 profile 时项目级提示，不静默回退。 |
| 5 | **默认页从「任务列表」改为「项目列表」，并保留「全部任务」与「未归入项目」。** 首屏先回答「我有哪几个项目、各自进展与负责人、哪个在等我」，再下钻。 | 用户当前的问题不是“任务列表不够多”，而是没有项目这一层；继续把扁平列表当首页，只会让层级继续不可见。 | 右侧栏任务页/面板回退页默认渲染项目列表；旧列表降为二级视图。计划树/图不再默认；是否保留为 `全部任务` 的次级入口由实现确认，本单不假装已有。 |
| 6 | **“待你处理”只指真正需要人的根任务动作，项目卡、任务行、通知抽屉读同一个投影。** 子任务等父负责人验收不是人的待处理；owner 还能处理的**子任务**阻塞也不算；根任务的 blocked/failed 本身就是人的决定。 | 现有 `attentionFor` 已经是这个保守语义；本项目视图必须复用，不能再造一个“待处理”计数。 | 项目卡 `待你处理 N` = 根任务 `attention` + 项目级负责人缺失；`有阻塞 M` 单独显示，不混入。 |
| 7 | **迁移结论：现有真实数据不能自动长出项目，也几乎没有子任务。** 2026-11-14 本地状态库只读聚合：92 个 Ticket、0 个有 `parentTicketId`、0 个根有子 Ticket、35 个标题带计划编号、0 个有 profile 快照。 | 项目是人的组织意图，不是标题/来源/计划编号的属性；子任务只在 owner 显式 `delegate` 时产生。用标题猜项目、用计划编号造层级，正是当前“层级看起来存在、数据里没有”的原因。 | 先发布只读项目视图 + 手工建项目/归入 + 负责人选择；随后改受理流程带 `projectId`，再谈自动建议（默认关闭）。没有这些前置，项目视图只能显示“未归入项目”。 |
| 8 | **不假装拥有宿主能力。** 项目视图仍落在插件右侧栏任务页/面板回退页；不改宿主导航、侧栏、通知中心；不预填宿主输入框；不做多人/跨设备。 | 公开扩展点只提供 `sidebar.right.pane.tab`、页头入口、`openSession`、插件自己的浮层/抽屉和插件自己的管理 API。 | 新任务/拆解通过主对话发起；页面内只做定位、复制建议句、读取与已有动作。写项目/归入/负责人属于后续插件 API，不包装成宿主能力。 |
| 9 | **分期：只读项目视图 → 手工项目与归入 → 受理带项目/负责人 → 拆解请求 → 通知归组 → 可选建议。** | 先把现有数据诚实展示出来，再改创建流程；否则先做自动归纳只会制造错误归属。 | 每期都有回退开关；关闭 `ux.projects.v1` 回到当前扁平任务页，目录文档保留、不删记录。 |

## 2. 数据模型核查

### 2.1 现有字段能直接支撑什么

| 能力 | 现有字段/投影 | 能否直接支撑项目视图 | 备注 |
| --- | --- | --- | --- |
| 多级任务 | `Ticket.parentTicketId`、`rootTicketId`、`delegation.parentTicketId` | 能，且是唯一正确的层级 | 只由 owner 显式 delegate 产生；真实数据为 0。 |
| 每级负责人 | `Ticket.profile`（受理时快照）、`TaskView.owner.profile`、`worker-<ticketId>` Session | 能显示“谁在做”，但不能表达“项目负责人” | 历史 Ticket 0 个有 profile；多数显示“默认执行配置”。 |

| 通知归属 | `noticeItems` 的任务 id | 部分；没有项目 id | 需要从 placement 解析，不新增通知实体。 |

### 2.2 为什么不能把项目做成根 Ticket

| 方案 | 问题 |
| --- | --- |
| 项目 = 一个根 Ticket，子任务 = 子 Ticket | 项目会被根的结束条件结束；一个任务完成不应当结束整条工作线。根 Ticket 需要 Mandate/Decision，项目却不需要授权。还会产生“项目负责人”与“根 owner”两套身份。 |
| 项目 = 一个 `TaskCategory`，完全自动归纳 | 自动归纳会把不相关任务并在一起；用户无法信任“这是我定义的项目”。当前 35 个标题带计划编号、0 个子任务，说明从标题猜结构不可靠。 |
| 项目 = 一个 Workspace/Space | Space 是执行目录/租约，不是任务组织；`SpaceKind 'project'` 是部署基线，不能从 Ticket 发明。 |
| 项目 = 第二个 `Subtask` 类型 | 会复制 Ticket 的类型、授权和结束条件；任务视图架构提案（`docs/tasks-view-architecture.zh.md`）已明确不新增 Subtask 类型。 |

### 2.3 必须新增的字段/结构（全部是加法）

| 结构 | 字段 | 说明 | 是否改 Ticket |
| --- | --- | --- | --- |
| 项目目录文档 `task-catalogue.v1`（KV） | `version`、`revision`、`projects[]`、`placements{}`、`history[]`、`updatedAt` | 一份原子读写的覆盖层；参照现有 `KV.profiles` 的做法。没有文档时读作空项目集。 | 否 |
| `Project` | `id`（`prj_…`）、`name`、`goal`（一句话）、`ownerProfileId?`、`state`（`active`/`archived`）、`order`、`createdAt`、`updatedAt`、`aliases?`、`revision` | `ownerProfileId` 指向 profile 的 head；空表示“默认执行配置”。项目不存 Mandate/Decision/Approval/交付物。 | 否 |
| `ProjectPlacement` | `ticketId`（只收根 Ticket）、`projectId`、`basis`（`manual`/`promoted`）、`updatedAt`、`updatedBy` | 一个根最多一个项目；子 Ticket 不单独归属，读时随根；review 随被审任务。 | 否 |
| `ProjectView`（`GET tasks` 新增） | `id`、`name`、`goal`、`owner?`、`state`、`counts`、`lastActivityAt`、`tasks`（根） | `counts`：`tasks`、`open`、`done`、`attention`、`blocked`、`failed`、`archived`；`attention` 只计人。 | 否 |
| `TaskView` 新增可选字段 | `projectId?`、`projectName?` | 只读投影；旧客户端忽略。子 Ticket 也带（从根继承），但项目计数只计根。 | 否 |
| `GET overview`/通知新增可选字段 | `projectId?`、`projectName?`、`rootTicketId?` | 通知归组；不改通知实体。 | 否 |
| 受理/创建流程 | `projectId?`、`ownerProfileId?` 的入参 | 受理时写 placement；owner 用项目当前 head 快照进 `Ticket.profile`。 | 否（只加请求字段与写入路径） |
| 项目级 attention | `{ kind: 'owner-missing', projectId }` | 只在项目设置的负责人配置不可用时出现；是项目元数据问题，不是 Ticket 状态。 | 否 |

**为什么不给 Ticket 加 `projectId`：** 归属是展示/组织元数据，不是授权或执行的一部分；放在独立 placement 里可以做到零 Ticket schema 变更、旧二进制安全、回退只删/忽略覆盖层。代价是受理时要多写一次 placement，读取时要 join；对这个单机、单用户的量级可以接受。

**为什么用 KV 而不是新表：** 现有 `KV` 已经用于 profiles（严格 Settings 之外的独立命名空间），读写有原子 `store.atomic` 和 revision。项目目录是同一类“显示/配置元数据”，不需要新的 SQL 关系、索引或迁移。未来多人/多端再考虑表化。

### 2.4 概念边界（“任务类别”到底指什么）

| 概念 | 数据来源 | 是否项目任务 | 有负责人 | 有授权 | 出现位置 |
| --- | --- | --- | --- | --- | --- |
| 项目 | `Project` 覆盖层 | 不是；是容器 | 是（默认绑定，不是权限） | 否 | 项目列表、项目详情标题 |
| 根 Ticket（任务） | `Ticket`（无 parent） | 是，项目树第一级 | 是（`profile` 快照） | 是（Mandate/Decision） | 项目详情、全部任务 |
| 子 Ticket（子任务） | `Ticket`（有 parent） | 是，第二级及更深 | 是（自己的 worker；Phase 1 继承根 profile） | 否，继承根 | 项目详情、任务详情 |
| review Ticket | `Ticket` + 标题/PR 归属 | 不是；挂在被审任务下 | 审查人 | 通常继承根 | 任务详情、审查行 |
| Assignment / Session / subagent | 执行记录 | 不是；执行细节 | 执行者 | 继承根 | 任务详情「执行会话」折叠 |
| 计划编号 `M1/T2-03` | 标题或 scope 的文本 | 不是；只是标签 | 无 | 无 | 计划树/图（E2），不进项目树 |
| Workspace / Space | `Execution.directory` | 不是；执行空间 | 无 | 写租约 | 空间诊断（E2），不进项目树 |

**结论：** 项目是第一层组织，根 Ticket 是第一层工作，子 Ticket 是第二层工作。计划编号、工作区、Session 都不能升格成项目或子任务节点。这个边界直接决定“何时能成为顶级项目”。

### 2.5 负责人绑定规则

1. **项目负责人是默认绑定，不是权限。** `Project.ownerProfileId` 只决定“这个项目新受理的根 Ticket 默认用哪个 profile”，不参与 Approval、Mandate、`maxActionLevel`、Eval、通知权限。项目负责人不能替人验收，也不能批准。
2. **新根 Ticket 在受理时快照。** 受理读取项目当前 head 的 profile 版本，写入 `Ticket.profile`，和现有“受理时冻结”的语义一致；之后项目换负责人不会改写旧 Ticket。
3. **已有 Ticket 不被改写。** 项目列表页头说明“项目负责人只约束之后的新任务”，项目卡负责人带 `title` 提示，设置框再次说明“已有任务按各自的配置执行”；任务行显示每个任务自己的负责人。不能把项目负责人当成所有任务的实际执行者。
4. **子 Ticket 继承根。** 沿用现有 Phase 1 规则：子 Ticket 绑定根 Ticket 的 profile；项目负责人不直接作用到子节点。未来允许子任务换 profile 是另一项能力，不在本设计。
5. **空/不可用：** 没有 `ownerProfileId` 读作“默认执行配置”（现有 legacy 行为）。如果配置了但 head 已停用/不存在，项目级 attention「负责人配置不可用」，新任务创建不静默回退；已有任务继续按自己的快照执行。
6. **真实数据前提：** 当前 0 个 Ticket 有 profile 快照；在配置 profile 之前，项目负责人只能选“默认执行配置”。原型里的命名负责人是目标态，不是对现状的假装。

### 2.6 不破坏现有接口与数据

- 不改 `Ticket`、`Mandate`、`Decision`、`Approval`、`Assignment`、`Delegation` 的任何字段或语义。
- `GET tasks` 保留 `tasks`、`milestones`、`totals`；只新增 `projects`、`unassigned` 和 `TaskView.projectId?`/`projectName?`。旧客户端忽略新字段。
- `GET tasks/:id` 的 `task`、`children` 不变；子节点读时带项目字段。
- `GET overview` 只加可选 `projectId`/`projectName`；通知实体（`noticeItems` 的 `Notice`）不新增持久化。
- 新写接口（建项目/改名/归档/归入/移出/换负责人）是加法；不在本单实现。
- 旧数据：没有 placement 的根 Ticket 读作“未归入项目”；没有项目文档时项目列表为空；旧二进制不读 KV 文档，不受影响。
- 回退：`ux.projects.v1` 关闭时完全回到当前任务页；项目目录保留，不删记录、不改 Ticket。

### 3.2 项目列表（默认页）

**首屏从上到下：**

1. **页头**：面板标签仍是 `任务`，页头标题是 `项目` + 说明「先看项目，再看每个项目里的任务。项目负责人只约束之后的新任务；已有任务按各自的配置执行。」；右侧 `全部任务`、`新建项目`（主按钮）。宽面板另有 `返回主对话`；侧栏里主对话就在旁边，不重复放。项目列表本身不搜索；搜索在 `全部任务` 页。
2. **待你处理条**（有则显示，最多 4 条）：
   - 标题：`等你处理` + 数字徽标；右侧 `全部 N`。
   - 每条：`验收`/`回答`/`处理` 标签 + 任务标题（可点）+ 项目名 + 时间 + 主按钮（`去验收`/`回答`/`重试`）。原因和后果在通知抽屉/任务详情里展开，首屏只给判断所需的最少信息。
   - 空态：`现在没有等你处理的事。有新结果或需要你确认时会出现在这里。`
3. **项目列表**（卡片堆叠；宽面板 2 列）：
   - 卡片头：项目名（可点）+ 状态 chip（`待你处理 2` 橙色 / `有阻塞 1` / `全部完成` / `已归档`）。
   - 一句话目标：最多两行，超出省略；`title` 属性保留全文。
   - 负责人行：头像（profile 首字）+ `负责人 开发负责人 · 第 2 版`（或 `默认执行配置`）；只有页头/提示里说明“只约束新任务”，卡面不把项目负责人写成执行人。
   - 进度：`1/4 顶层任务完成` + 细进度条；分母明确是**顶层任务**（A 的 6 个节点里只数 4 个根，不把子任务算进分母）。子任务完成度在项目详情的行内看，不在卡上叠加。没有任务时不画进度条，卡头显示 `还没有任务`。
   - 待办行：`待你 验收「支付接入」 · 回答「数据迁移」`，每个都可点；没有时显示 `现在不需要你 · 负责人推进中`。项目级负责人配置不可用时，第一行是 `修负责人配置「项目」`。
   - 阻塞行（可选）：`阻塞：等激光雷达到货；供应商预计 2 天。`；与“待你处理”分开。
   - 页脚：`12 分钟前 · 支付接入已就绪` + 来源 chip（`对话`/`GitHub`/`飞书`）；不显示计划编号、Session id。
4. **未归入项目**：
   - 默认一条紧凑条：`未归入项目 2 个任务 · 任务名（状态）…` + `全部处理`；不占首屏。
   - 点 `全部处理` 进入未归入页；页内每行有状态、负责人、`归入项目`；没有项目时显示 `新建项目并归入`。
   - 这是迁移入口，不隐藏；旧数据全部在这里，直到人工归入。
5. **已归档**：一条链接 `已归档 1 个项目`，进入只读列表；详情 `更多 → 恢复`，返回回到 `已归档` 列表。不占首屏。

**排序：**

1. 有“待你处理”的项目在前，按 `attention` 降序。
2. 其次按 `blocked` 降序。
3. 再按 `updatedAt`（最近活动时间）降序。
4. 名字只作为最后的稳定排序，不按名字默认排。

**空态（没有项目）：**

```
还没有项目。
项目是一条持续的工作线，不是一次任务。告诉小助你要推进什么，
例如「帮我盯 A 系统开发」；已有任务也可以在下面归入新项目。
[让小助建项目]  [查看全部任务]
```

**为什么项目列表不用表格：** 项目数量少（个位数到十几个），每张卡需要同时表达目标、负责人、进度、待办、阻塞和最近活动；表格会把这些压成列，首屏更难读。卡片列表在 620px 右侧栏也能单列工作。

**从当前首屏移走什么（取舍）：**

- **主 Agent 大卡**不再占项目列表首屏；侧栏里主对话就在旁边，宽面板保留 `返回主对话`。换头像/主 Agent 设置仍在主对话/设置，不搬进任务页。
- **顶部 `通知 / 文件 / 设置` tab** 不再出现在项目页；它们仍是主对话/插件页的入口，项目页只负责任务视图，不复制全局导航。通知中心按 §4.6 保留。
- **入门说明卡**可保留为一次性提示，不占列表首屏；当前截图里的“知道了”卡不再默认出现。
- **列表 / 任务树 / 计划树 / 图切换**不再作为项目页首屏；项目树表达层级，`全部任务`保留**顶层**扁平查找；子任务在项目详情展开，筛选只统计顶层任务。计划树/图如果仍需要，作为 `全部任务` 的次级入口，由实现确认；本单原型只画列表。
- **生成时间/刷新**不帮助“哪个项目在等我”的判断，移到 `全部任务` 或设置。
- 这些是设计取舍，不是已实现；如果产品要求保留主 Agent 卡，可以放在页头下方折叠，而不是回到列表首屏。

### 3.3 项目详情

**头部：**

```
‹ 项目
A 系统开发                                  [更多]
把内部工单系统迁到新架构，12 月中旬前完成切换
负责人 开发负责人 · 第 2 版    4 个顶层任务 · 1/4 完成    12 分钟前更新
```

- `更多`：`编辑目标`、`换负责人`、`归档项目`（本期设计，写接口后续；在只读阶段隐藏或置灰并说明）。**归档只允许在没有未结束任务、没有待你处理任务时使用**；否则按钮置灰并说明“先处理或结束它们，归档不会隐藏待办”。
- 头部下方是**待你处理带**（0–N 条；原型 A 为 2 条），与项目列表的待办行同源；点击直达任务详情并聚焦动作。超过首屏时滚动，不截断计数。
- 再下面是**任务树**（见下）和**最近活动**（宽面板右栏；窄面板在树下方顺序排列，不做折叠）。

**任务树：**

```
顶层任务 4                                  [展开全部子任务]
▾ 登录改版            进行中    开发负责人 · 第 2 版    2 个子任务 · 1 个完成    刚刚
   ● 接口鉴权          已完成    鉴权负责人 · 第 1 版    已由上级负责人接受
   ● 错误提示文案      等上级验收 文案负责人 · 第 3 版    已向开发负责人汇报    08:20
▸ 支付接入            待你验收  支付负责人 · 第 1 版    交付已就绪
▸ 数据迁移            待你回答  数据负责人 · 第 2 版    等你回答问题
已完成 1
● 权限梳理            已完成    权限负责人 · 第 1 版    昨天
```

- 第一级只放根 Ticket（界面叫“顶层任务”）；**review Ticket 不作为项目任务**。任务行的状态已经表达“待人验收/等上级验收”；独立 review 票据的 `1 个审查` chip 在实现中加，原型未画。子任务才算第二级。
- 有子任务的行显示 chevron；默认展开“有待你处理”的根和第一个根，其余折叠。展开只加载 `GET tasks/:id?depth=1`；更深层在任务详情里继续展开，避免一次拉全树。
- 每个节点：状态点/标签 + 标题 + 负责人 + 子任务进度或最近汇报 + 时间。子节点缩进约 20px，左侧有一条 1px 的层级线，不使用卡片套卡片。
- 子任务状态用 `已完成`、`进行中`、`等上级验收`、`被卡住（上级处理）`、`失败（上级处理）`；只有升级到人的失败/阻塞才在根行显示 `需要你处理`。
- 没有子任务的行不显示空 chevron；任务详情里给 `请负责人拆解` 的说明入口（见 §3.6）。
- 树不显示计划编号、Assignment、Session id、trace id；这些在任务详情的 E2 折叠区。

**最近活动：**

- 5 条以内：`时间 · 任务标题 · 一句话事件`（例如「负责人汇报了结果」「父负责人接受了子任务」「交付物更新到 r2」）。
- 点击跳到对应任务；不显示原始日志、模型名、token。
- 没有活动：`刚建项目，还没有活动。`

### 3.4 任务 / 子任务详情

**共同排序（人读的顺序）：**

1. 返回链接回到**来源**：`‹ 项目`（项目列表）、`‹ A 系统开发`（项目详情）、`‹ 待你处理`（抽屉）、`‹ 全部任务`、`‹ 未归入项目`；子任务回到父任务。实现可升级成 `项目 / A 系统开发 / 支付接入` 面包屑，但原型先用返回链接。
2. 标题、状态、来源、负责人（子任务同时显示上级负责人）。
3. **需要你做什么**（仅当人待处理）：一句结论 + 一个主按钮 + 一个次按钮 + 不处理的后果。
4. **结果 / 交付物**：一句话结果、交付物列表（类型、ref、版本、打开）、验收条件（规则/人工确认分组）。子任务的交付物标明“由上级负责人接受”，不出现人的批准按钮。
5. **下一步 / 预计**：只在非待人处理时单独显示（如 `等负责人继续，现在不需要你`）；待人处理的下一步和后果写在上面的动作卡里，避免重复。时间只写记录里有的，不编。
6. **谁在做**：执行负责人 profile + 角色；子任务加上级负责人；profile 未知时写“默认执行配置”，不暴露内部 id。
7. **子任务**（有子节点就显示，包括子任务自己）：每个子节点一行，点击进入子任务详情看汇报/判断/交付；深层子任务继续同样的入口，最多到现有的 5 层。叶子子任务不显示空的“子任务”节。`请负责人拆解` 的入口放在这一节末尾。
8. **阻塞 / 向上汇报**：阻塞原因和等待方写在顶部 note（`有 1 个任务被阻塞，负责人处理中`）；父的判断历史（接受/退回/改派/自干/升级）放在汇报历史，用人的话写，不显示 trace id。
9. **汇报历史**：按时间倒序，最多展示最近若干条；每条 `谁 · 做了什么 · 结果`。
10. **来源**：对话/飞书/GitHub/邮件等 chip；打开原线程。
11. **执行会话**：默认折叠；`打开执行会话`（现有 `openSession`），以及技术详情（E2）。

**关键正确性：**

- 子任务的“完成”只代表交付给父负责人；默认面写 `已向开发负责人汇报`，不写“已完成/已验收”。父负责人接受后写 `已由上级负责人接受`，仍不等于人的最终验收。原型里子任务详情只有一条绿色完成 note，不再重复第二条“等上级”说明。
- 人的验收按钮只出现在根任务；子任务详情不提供 `批准`，避免绕过父审查链。
- 被阻塞的**子任务**且祖先 owner 还能处理时，不显示“待你处理”，显示 `等负责人处理`；根任务 blocked/failed 直接进“待你处理”，因为根已经停下，只有人能决定重试/停止/改派。
- 轻量 Ticket 没有 owner/worker/子任务；显示 `轻量执行`，不伪造负责人。

### 3.5 交互、窄宽与无障碍

- **下钻/返回**：点击项目卡进详情；点任务行进详情；返回链接回到来源（项目列表、项目详情、全部任务、未归入、待你处理），子任务回父任务；`Esc` 从抽屉/弹窗返回列表；返回保留展开状态（原型会回到顶部，实现需保留滚动位置）。
- **选中态**：右侧栏一次只显示一个详情；宽面板项目详情是树 + 最近活动两栏，任务详情仍是单列。窄宽度压成单列，详情替换列表，顶部返回。
- **键盘**：项目名是 `<button>`（Enter/Space 打开）；整卡可点作为鼠标便利，卡内动作按钮不嵌在链接里。任务主体是 `<button>`，展开/收起是独立可聚焦按钮；抽屉 `Esc` 关闭并还原到触发点；动作确认框先聚焦主按钮，危险动作先聚焦取消。
- **响应式**：宽面板（宿主宽度 > 1180）项目卡两列、项目详情树 + 活动两栏；右侧栏 624 与 620 窄面板单列；< 620px 只做了 CSS 约束，未做真机验证，页头动作也还未收进“更多”。不横向溢出。
- **状态轮询**：沿用 `TasksViewClient` 的 5 秒轮询；详情按需加载；通知/待办与任务列表同源，避免两个计数。
- **动作反馈**：成功 toast + 列表/抽屉/项目卡同步更新；失败保留条目并显示具体原因（不乐观删除）；审批失败（revision 变化）提示“交付已更新，请重看”。

### 3.6 规则：项目、任务、子任务怎么产生

#### 何时能成为“顶级项目”

必须同时满足：

1. **人明确命名并给出一句话目标**（或从小助的建议里确认）；项目名不是任务标题的自动截断。
2. **有一个负责人**：一个 profile 的 head，或显式选择“默认执行配置”。
3. **至少一个根任务，或明确是“还没有任务的规划项目”**；空项目允许，但卡片必须显示“还没有任务”。
4. **不是单次任务、review Ticket、子 Ticket、计划编号、Workspace/Space**。

允许“把一个已有根任务提升为项目”：用任务标题作项目名、任务 Goal 作目标、任务 profile 作负责人，然后写入 placement。**不新建 Ticket、不改授权、不复制交付物。**

不允许：

- 按标题/计划编号/来源/工作区自动新建项目。
- 把 review Ticket 或子 Ticket 当作顶级项目。
- 项目嵌套项目（v1 不做子项目）。
- 自动把“同一来源的多个任务”归成一个项目；最多在人工确认后建议。

自动建议（可选，默认关闭）：只有 ≥2 个根 Ticket 且出现同一个显式项目名/明确托付时才提示「这 3 个任务像同一个项目，要建项目吗？」；建议永不自动写入，也不改已有归属。

#### 任务（根 Ticket）怎么创建

- 走现有受理路径：人在主对话/来源里提出请求 → Eval/Decision → 根 Ticket；**项目归属在受理时作为 metadata 写入 placement**，不改变授权。
- 人在项目上下文里说“在 A 系统开发里做 X”时，主 Agent 把 `projectId` 带进受理；项目卡的新任务入口只负责打开主对话并给出建议句，不在页面内直接造 Ticket（宿主没有预填输入框的扩展点）。
- 已有未归入的根 Ticket：在“未归入项目”里选项目；或从任务详情“提升为项目”。不改 Ticket 本身。
- 根 Ticket 结束后项目不自动结束；项目由人归档。

#### 子任务怎么创建

| 方式 | 谁发起 | 是否自动 | 结果 |
| --- | --- | --- | --- |
| 父 owner 在运行时拆解 | 根/子 Ticket 的 owner | 是（owner 决定，不是视图决定） | 调用现有 `orchestrator_child`，子 Ticket 有独立 owner/worker，继承根授权，向父汇报。 |
| 人请求拆解 | 人 | 否 | 在任务详情/对话里说“请负责人拆解”；作为给 owner 的输入，由 owner 决定是否/如何拆。视图不直接创建无 owner 的节点。 |
| 标题/计划编号派生 | 无 | **不允许** | 计划树/图只是标签，不生成 Ticket。 |
| review 自动挂载 | 现有审查流程 | 是 | review Ticket 挂被审任务，不算项目任务。 |
| subagent/Session 派生 | 执行器 | 否 | 只是执行细节，不成为任务节点。 |

**为什么层级会变多/变少：** 只有 owner 认为工作需要独立负责人、独立交付和独立汇报时才拆；没有拆的任务保持叶子，这是诚实的。项目视图提供“请负责人拆解”的入口，但不把“拆”变成 UI 的强制步骤，避免制造空壳子任务。

**拆分上限（沿用现有）：** 深度最多 5 层、直接子节点宽度和单根 live 子节点配额由 kernel 现有约束控制；视图不绕过。

## 4. 通知与待处理

### 4.1 什么事件主动打扰人

| 事件 | 主动打扰（浮层/弹窗） | 归属 | 说明 |
| --- | --- | --- | --- |
| 根任务交付就绪，待人验收 | 是，一次 | 项目 + 根 | 人的验收只在这里。 |
| 根任务提出需要人回答的问题 | 是，一次 | 项目 + 根 | 问题原文来自 `Attention.question`。 |
| 根任务失败/阻塞 | 是，一次 | 项目 + 根 | 根任务已经停下，必须人决定重试/停止/改派。 |
| 子任务失败/阻塞，且没有在世祖先 owner | 是，一次，合并到根 | 项目 + 根（附子任务名） | 不单独给子任务发第二条通知。 |
| 项目负责人配置不可用/已停用 | 是，一次 | 项目 | 影响未来任务的默认 owner，不是某个任务失败。 |
| 子任务就绪，等父负责人验收 | **否** | 父 owner 队列 | 任务树显示「等上级验收」；不是人的待处理。 |
| 常规进度（开始/进行中/子任务接受） | **否** | 项目活动 | 只进最近活动；不打断。 |
| 根任务完成/合并结果 | **否**（建议） | 通知中心“进展”组 | 现有实现会 `pop` 结果；本设计建议结果不弹，只在通知中心和项目卡更新。是否改是行为取舍，见 §9。 |
| 项目全部完成 | **否** | 项目卡 | 可建议归档，不弹窗。 |
| 归入/换负责人/改名 | **否** | 项目活动 | 元数据变更，不产生通知。 |

原则：**只在“需要人做决定/验收/补信息，且 owner 做不了”时打扰。** 根任务 blocked/failed 本身就是人的决定；只有**子任务** blocked/failed 且祖先 owner 还能处理时才保持安静。其余用项目卡、任务行、最近活动表达；不用“进度播报”占注意力。

### 4.2 通知如何归到项目/任务

- 每条通知（`Notice`）新增可选 `projectId`、`projectName`、`rootTicketId`、`childTicketId?`；由 placement 解析，不新增通知表。
- **一个根任务至多一条待人通知**：同一根的 review/answer/failure 更新同一条，不叠加；子任务升级合并到根，副标题写 `来自子任务：回调签名`。
- 项目卡 `待你处理 N` = 该项目下不同根任务的待人通知数 + 项目级负责人问题（最多 1）；任务行和抽屉读同一个投影，三处数字必须一致。原型 fixture 没有负责人不可用的项目，项目级这一条用注入数据验证过项目卡/首屏待你条/抽屉组第一行，但没有截图。
- 抽屉分组：`项目名（N）` → 通知条目；没有项目的任务归到 `未归入项目（N）`；项目级负责人问题作为项目组的第一条，不混进顶层任务数。
- 同一任务的通知跨项目移动时，下一次轮询按新 placement 归组；不保留旧项目副本。
- 已读/未读仍按浏览器已读集合（现有实现），不新增服务端已读表。

### 4.3 “待处理”如何识别

沿用现有 `attentionFor`，不按状态猜：

| 条件 | 是否人的待处理 | 依据 |
| --- | --- | --- |
| 根任务 `review`（交付待人验收） | 是 | `Attention`/`review` 投影 |
| 根任务 `answer`（有 `Attention.question`） | 是 | `Ticket.attention` |
| 根任务 `delivery`（消息未送达） | 是 | `attentionFor` |
| 根任务 `blocked`/`failed` | 是 | 根任务已经停下，只有人能决定重试/停止/改派 |
| 根 `endPending` 且 owner 不可用 | 是 | `attentionFor` |
| 子任务 `review`（等父验收） | 否 | 父 owner 的队列 |
| 子任务 `blocked`/`failed` 但祖先是可用 owner | 否 | 祖先 owner 处理；B 的避障子任务属于这一类 |
| 子任务 `blocked`/`failed` 且无可用祖先 owner | 是，升级到根 | `attentionFor` 现有规则 |
| `working`/`queued`/`idle` | 否 | 不需要人 |
| 项目负责人缺失/停用 | 项目级是 | 本设计新增，显式元数据问题 |

**解释“为什么是我”的三段式（复用现有 Notice 字段）：**

- `what`：发生了什么、对象是谁、证据是什么（交付物/问题原文/失败原因）。
- `next`：你能做什么，一个主按钮 + 一个次按钮。
- `consequence`：不处理会怎样（一直停在这里/任务结束/重开执行），不夸大、不编时间。

### 4.4 具体文案与层级

| 场景 | 标题 | what | next | consequence | 主/次动作 |
| --- | --- | --- | --- | --- | --- |
| 待人验收 | `「支付接入」的交付已就绪` | `支付回调已接通，灰度 10% 验证通过；2 个文件、2 条验收条件。` | `查看并验收，或退回修改。` | `不处理会一直停在这里，负责人不会继续。` | `去验收` / `查看任务` |
| 待人回答 | `「数据迁移」需要你回答` | `历史订单要保留几年？只读查询要不要一起保留？` | `回答后负责人继续。` | `不回答，这个任务会一直停在这里。` | `回答` / `查看任务` |
| 根失败/阻塞 | `「整理迁移说明」失败了，负责人已停止` | `连续 2 次失败：没有权限读取迁移目录。` | `重试会重新开始；停止会结束这个任务。` | `不处理，任务会停在失败状态。` | `重试` / `查看任务` |
| 子任务升级 | `「A 系统开发 › 支付接入 › 回调签名」卡住了` | `子任务失败，上级负责人不可用。` | `查看并处理：退回重试、改派或停止。` | `子任务不会自己恢复。` | `查看并处理` |
| 子任务等父验收 | 任务树行：`等上级验收` | `已向开发负责人汇报，等它判断。` | — | — | 不是通知 |
| 项目负责人不可用 | `「B 桌面机器人研究」的负责人配置不可用` | `原负责人配置已停用；新任务无法绑定它。` | `选择一个负责人，或显式使用默认配置。` | `已有任务不受影响；新任务要等你选。` | `选择负责人` |
| 项目全部完成 | 项目卡：`全部完成` | `4/4 个顶层任务结束。` | `可以归档项目。` | — | `归档`（可选） |
| 无待办 | `现在没有等你处理的事。` | `有新结果或需要你确认时会出现在这里。` | — | — | — |
| 通知抽屉说明 | `只显示真正等你决定、验收或补信息的任务；其余进展留在任务和项目里。` | — | — | — | — |

层级：

- **项目卡**：只放计数和一句待办摘要，不展开长文案。
- **项目详情**：待办带一行一条，显示当前全部待人项（原型 A 为 2 条）；更多时靠滚动，不截断计数。
- **任务详情**：动作卡写结论/下一步/后果；交付物、验收条件、汇报历史分别承载证据。
- **通知抽屉**：项目分组 + 条目三段式；同一根的重复事件合并。
- **浮层**：只显示最新一条待人事件，标题 + 一个主按钮 + `查看全部`；不显示进度。原型用抽屉演示，浮层只做文案设计，见 §7.3。

抽屉只给**主动作 + 查看任务**；退回/停止等次动作留在任务详情/确认框里，避免在通知里误触。

### 4.5 一键处理与失败

| 动作 | 现有能力 | 设计 |
| --- | --- | --- |
| 验收/批准 | `POST tickets/:id/approve`（带 revision） | 确认框展示交付摘要/验收条件；确认后结束根任务。revision 变化时拒绝并提示“交付已更新，请重看”。 |
| 退回 | **没有专用 HTTP 动作**；现有是 `Decision.kind='reopen'`（续做/重新受理），不是 review 页的一键退回 | 一期只提供「填一句原因 + 定位到现有重开路径」，不假装页内已能提交；新增 `POST tickets/:id/return` 后再升级。原型弹窗标注目标态。 |
| 重试 | `POST tickets/:id/retry` | 确认后新 attempt；失败保留通知并显示原因。 |
| 停止 | `POST tickets/:id/stop` | 确认；结束任务/子任务链按现有规则。 |
| 回答 | 现在：打开来源线程/触发页；**没有 `POST tickets/:id/answer`** | 一期“一键定位到可回答处”，并复制问题建议句；如果后续加 answer API，再升级为页内回答。原型里的“提交回答”标注原型/目标态，不能看起来已经能发。 |
| 归入项目/建项目 | 本设计新增写接口（未实现） | 选择项目/新建；只写 placement/目录，不改 Ticket；失败回滚，不乐观删除。 |
| 换负责人 | 本设计新增写接口（未实现） | 只影响未来受理；已有任务不变；成功 toast 说明影响范围。 |

**动作后反馈：**

- 成功：toast + 三处计数同步更新；如果任务结束，项目卡进度加一，待办少一条。
- 失败：保留条目，显示具体错误和重试入口；不能把失败当成功。
- 批量：`全部 N` 打开抽屉逐条处理；v1 不做“一键全部批准”（验收必须逐条看交付）。

### 4.6 与现有通知的关系

- 本设计的“待你处理”抽屉只承载 `attention`（人必须行动的事），**不是完整通知中心**。现有 `noticeItems` 的 `attention/progress/system` 分组和通知中心不删除；`progress/system` 仍在原通知中心查看，后续再按项目归组。
- 系统问题（来源错误、设置问题）仍归 `system`，不强行归项目；如果系统问题影响多个项目，在原通知中心顶部单独一组。
- 任务通知的动作保持现有 `view/approve/retry` 等；新增 `answer`（定位）和 `assign-project`（归入）是后续写路径。
- 现有结果通知 `pop: true` 的建议改法是行为取舍（§9），不在本单实现。原型不演示浮层，只用抽屉和首屏待办条。

| 预填主对话输入框/在页面内直接造 Ticket | **不可用（当前无扩展点）** | 设计为打开主对话 + 建议句；不假装。 |
| 替换宿主导航/侧栏/工作区/设置 | **不可用** | [022](022-harness-extension-requests.zh.md)、[028](028-plugin-main-page.zh.md) §4。 |
| 宿主原生通知中心/全局未读一级入口 | **不可用** | 插件浮层/抽屉是自有 surface；不写成宿主能力。 |
| 多人、成员、角色、跨设备 | **不在模型内** | 当前单用户本地；项目没有成员表，不做。 |
| 项目嵌套/子项目 | **不做（v1）** | 没有数据模型；用户要的是顶级项目 → 任务。 |
| 自动归类/LLM 建议 | **可选、默认关闭** | 只有人工确认才写；建议不是事实。 |

**结论：** 只读项目视图与通知归组不需要宿主改动；真正的新任务是“项目目录 + placement + 受理带项目”的插件/kernel 写入能力。设计不把写能力包装成宿主已支持，也不为了视觉隐藏宿主 chrome。

## 6. 迁移可行性：从现有数据能不能长出层级

### 6.1 真实数据结论

| 问题 | 结论 | 证据 |
| --- | --- | --- |
| 现有数据能生成项目吗？ | **不能，除非人工建。** 没有一个项目字段；标题/来源/scope 都没有“项目”语义。 | 项目代码为空；真实数据无项目记录。 |
| 现有数据能生成子任务吗？ | **只有已经存在的子 Ticket。** 当前为 0；不能从计划树、subagent Session、标题缩进追溯。 | `parentTicketId` 非空 0；`delegation` 只由 owner 显式创建。 |
| 计划树/图能当项目树吗？ | **不能。** 它们是标题/scope 的计划标签，35 个标题带标签、40 个 scope 带标签，但 0 个子 Ticket。 | `ownership.ts` 的 `planOf` 只读文本；不写数据。 |
| 子任务为什么少？ | 创建需要 owner 在运行时显式 `orchestrator_child`；视图不提供拆解入口；没有项目上下文提示“这条线还要拆”。 | `orchestrator_child` 工具、现有任务页只展示一层子节点。 |
| owner 能直接显示吗？ | **多数不能。** 0 个 Ticket 有 profile 快照；历史/当前任务显示“默认执行配置”。 | 真实数据聚合；`Ticket.profile` 可选。 |

**所以迁移顺序必须是：先人工建项目和归入，再让受理带项目，最后才是自动建议。** 直接上“自动生成项目/子任务”只会把猜测写进数据，比现在的扁平列表更糟。

### 6.2 分阶段迁移

| 阶段 | 交付 | 数据写入 | 验收 |
| --- | --- | --- | --- |
| P0 只读 | 项目列表/详情/任务树读取；没有项目时显示“未归入项目”；不写入 | 无；读空目录 | 现有任务不被隐藏；回退开关可回旧列表。 |
| P1 手工项目 | 建项目/改名/目标/归档；根任务归入/移出；提升任务为项目；负责人选择 | 只写 `task-catalogue.v1` | 旧数据全部在未归入；归入后立刻出现在项目；Ticket 不变。 |
| P2 受理带项目 | 受理请求带 `projectId`；新根任务默认 owner 快照；主对话带项目上下文 | placement + Ticket.profile（正常受理） | 新任务自动出现在项目；旧任务不改；没有项目时仍落未归入。 |
| P3 拆解请求 | 任务详情的“请负责人拆解”作为 owner 输入；owner 用现有 `orchestrator_child` | 正常 delegation | 不产生空壳子任务；子任务有 owner、向父汇报。 |
| P4 通知归组 | notice 带 projectId；项目卡/详情/抽屉三处一致；项目级 owner 问题 | 无新增持久化 | 计数一致；子任务父审不打扰人。 |
| P5 可选建议 | ≥2 个根任务的归组建议，默认关闭，人工确认才写 | 只在确认后写 placement | 不自动建项目；可关闭/回退。 |

### 6.3 必须先改的创建流程

没有 P1/P2，项目视图会是一个几乎空的壳：真实数据 92 个 Ticket 全在“未归入项目”，0 个子任务。因此：

1. **先做 P1**，让人能把现有任务归入项目并建项目；这不需要改 Ticket，也不需要新授权。
2. **P2 在受理/派发路径加 `projectId` 和项目默认 owner**；这是新项目自动长出来的前提。主对话/来源里要能说“在 A 系统开发里做 X”。
3. **P3 的拆解必须由 owner 发起**；视图只提供请求入口。不要把“拆解”做成 UI 自动建节点。
4. 通知归组可以并行做，但必须等 placement 可读，否则没有项目可归。

### 6.4 兼容、回退与不变量

- **不变量**：项目不是授权根；子 Ticket 没有 Mandate/Decision；Approval/outbox 的 `ticketId` 仍是根；项目/placement 不进入 prompt 装配；项目不产生成员关系。
- **兼容**：Ticket 字段零变更；`GET tasks` 旧字段保留；旧客户端忽略新字段；旧二进制不读 KV 目录。
- **回退**：关 `ux.projects.v1` → 旧任务页；目录文档保留；不删任务、不删归属；重新打开开关恢复。写接口失败 → 不改任何 Ticket/授权记录；placement 写入是原子的。
- **损坏处理**：项目目录解析失败时项目视图回退到“未归入项目”并提示，不覆盖文档；placement 指向不存在的项目/Ticket 时读作未归入；不猜项目。
- **审计**：目录 `history` 记录人工 `create/rename/move/archive/owner-change`；不写 activity，不触发 Eval/通知；如后续需要事件流，再加只读投影。

## 7. 可点击原型与同视口证据

### 7.1 原型

## 8. 验证与独立 review

### 8.1 自查（对应工单 ⑥）

1. **是否真的看得清项目与负责人？** 项目卡首屏同时有项目名、一句话目标、负责人、进度、待办、阻塞、最近活动；负责人是 profile 的当前 head（或明确的“默认执行配置”），不是会话 id。真实数据没有 profile 时，界面如实显示默认配置，不假装有具名负责人。
2. **下钻是否自然？** 项目 → 顶层任务 → 子任务；返回链接回到来源并保留展开状态；子任务只在真实 delegation 存在时出现，没有子任务就是叶子；不把计划编号/工作区/subagent 伪装成层级。
3. **待处理是否可操作？** 每条有明确主动作和必要的次动作，带 what/next/consequence；验收/重试/停止在任务详情/确认框里一键完成；回答是“一键定位到可回答处”，页内回答标注为后续写路径；子任务等父审不打扰人；项目卡/详情/抽屉计数同源。
4. **数据判断是否准确？** 真实聚合 92/0/0；35 个计划标签不是层级；0 个 profile 快照；结论都有代码或聚合依据。
5. **是否破坏现有接口/数据？** 只加 KV 覆盖层和可选投影字段；Ticket 零改动；旧客户端忽略；开关可回退。
6. **是否假装拥有宿主能力？** 没有：任务页仍在右侧栏/面板；新任务/拆解走主对话；不预填输入框；不替换宿主导航/通知中心；不做多人/跨设备。

### 8.3 已知限制

- 这是设计/原型，不是实现；项目创建/归入/换负责人/页内回答都还没有代码。
- 真实数据没有项目、没有子 Ticket、没有 profile 快照；P1 之前项目视图只能显示“未归入项目”。
- 自动建议默认关闭，且永远不自动写；如果产品要求“自动长出项目”，需要先定义可信的项目信号和人工确认门，不能靠标题猜。
- 现有结果通知会弹浮层；本设计建议改为安静结果，属于行为取舍，需要产品确认。
- 窄宽度（<620px）只做了 CSS 规划，未做真机/移动端验证。
- Before/After 不是同一 fixture；主对照是 1440×900 的宽面板任务列表，其余对照已在 §7.2 标明限制。

## 9. 待确认的产品取舍

1. **项目负责人是 worker profile 还是人？** 当前模型没有人类 owner 字段；本设计选 profile（与 Ticket.profile 一致）。若产品要“人作为负责人”，需要新增身份/成员模型，超出本单。
2. **结果通知是否还弹浮层？** 本设计建议只有“需要人行动”才弹，结果进通知中心/项目卡；这会改变现有 `pop: true` 的结果通知行为。
3. **是否允许空项目？** 本设计允许（规划用），但卡片必须显示“还没有任务”；若产品希望项目必须至少一个任务，改创建校验即可。
4. **页内回答是否要做？** 目标态是 `POST tickets/:id/answer` 写 human input；如果先不做，就保持“打开来源线程 + 复制建议句”，不要伪装成一键发送。
5. **项目是否自动归档？** 本设计只建议，不自动；全部完成的项目仍显示在列表，直到人归档。
6. **是否支持子项目/项目嵌套？** v1 不做；用户要的是顶级项目 → 任务 → 子任务。若未来要做，需要另立层级模型。
7. **是否允许强制归档仍有未结束/待人任务的项目？** v1 **不允许**：归档按钮在这种情况下置灰，因为归档会让这些任务从首屏、“全部任务”和抽屉里消失。若产品要提供“强制归档”，需要同时决定待办迁移/提醒，不能静默隐藏。
